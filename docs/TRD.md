## 2. 기술 스택과 선택 이유

| 기술 | 역할 | 왜 골랐나 |
| --- | --- | --- |
| Next.js 15 (App Router) | 웹 앱의 뼈대 | 화면과 API를 한 프로젝트 안에서 같이 만들 수 있어서 처음 배우기에 편하다. |
| React 19 | 화면 만들기 | 화면을 작은 부품(컴포넌트)으로 나눠 만들 수 있고, 자료와 예제가 가장 많다. |
| TypeScript (strict) | 프로그래밍 언어 | 값의 종류(타입)를 미리 검사해서 실행 전에 실수를 찾아준다. |
| Tailwind CSS | 화면 꾸미기 | CSS 파일을 따로 만들지 않고 태그에 클래스 이름만 붙여서 꾸밀 수 있다. |
| Zod | 입력값 검사 | "제목은 1~100자" 같은 규칙을 한 곳에 적어 두고 화면과 서버에서 같이 쓸 수 있다. |
| Postgres (Neon) | 데이터 저장소(DB) | 널리 쓰이는 DB이고, Neon은 설치 없이 인터넷에서 바로 무료로 쓸 수 있다. |
| Drizzle ORM | DB와 대화하는 도구 | SQL을 TypeScript 코드처럼 쓸 수 있고, 타입 검사도 받을 수 있다. |
| Jest + React Testing Library | 테스트 | 기능이 제대로 동작하는지 자동으로 확인한다. RTL은 사용자가 화면을 쓰는 방식 그대로 테스트한다. |

## 3. 버전별 저장 방식

PRD의 기능은 같지만, 할 일을 어디에 저장하는지가 버전마다 다르다.

| 버전 | 저장 위치 | 새로고침하면 |
| --- | --- | --- |
| v0.1 | 브라우저 메모리 (React 상태) | 사라진다 (PRD 7절의 확인 필요 사항) |
| v0.2 | 서버 메모리 (API 라우트 안의 배열) | 남는다. 서버를 다시 켜면 사라진다. |
| v0.3 | Postgres DB | 남는다. 서버를 다시 켜도 남는다. |

- Drizzle과 Neon은 v0.3부터 쓴다. v0.1, v0.2에서는 설치하지 않는다.
- 4절의 흐름은 v0.3 기준이다. v0.2는 6~8단계가 "서버 메모리 배열에 넣기"로 바뀐다.

## 4. 할 일 추가 흐름 (버튼 클릭부터 DB 저장까지)

예시 기능: F-01 할 일 추가

1. **입력:** 사용자가 입력창에 제목을 쓴다. (`src/components/`의 컴포넌트)
2. **클릭:** 사용자가 "추가" 버튼을 누른다. 컴포넌트가 클릭 이벤트를 받는다.
3. **화면에서 1차 검사:** 컴포넌트가 Zod 규칙으로 제목을 검사한다. 규칙에 맞지 않으면 서버로 보내지 않고 화면에 안내 문구를 보여준다.
4. **서버로 요청:** 컴포넌트가 `fetch`로 API 라우트(`app/` 아래)에 제목을 JSON 형식으로 보낸다.
5. **서버에서 2차 검사:** API 라우트가 같은 Zod 규칙으로 다시 검사한다. 화면 검사는 우회될 수 있어서 서버에서도 검사한다. 맞지 않으면 오류 응답을 돌려준다.
6. **서버 로직 호출:** API 라우트가 `src/lib/`의 저장 함수를 부른다.
7. **DB 명령 만들기:** 저장 함수가 Drizzle로 "할 일 한 줄 추가" 명령(SQL)을 만든다.
8. **DB 저장:** Drizzle이 Neon의 Postgres로 명령을 보낸다. DB가 할 일을 저장하고 ID와 생성 시각을 붙인다.
9. **결과 응답:** DB가 저장된 할 일을 돌려준다. API 라우트는 그 할 일을 JSON으로 화면에 보낸다.
10. **화면 갱신:** 컴포넌트가 응답을 받아 할 일을 목록 맨 위에 넣는다. (F-02 최신순) 입력창은 비운다.
11. **새로고침 시:** 페이지가 API로 목록을 요청한다. 서버가 DB에서 생성 시각이 늦은 순서로 읽어 돌려준다. (F-05)

완료 전환(F-03)과 삭제(F-04)도 같은 순서를 따른다. 다른 점은 7단계의 DB 명령이 "수정"이나 "삭제"라는 것이다.

## 5. 폴더 구조와 역할

| 폴더 | 들어가는 것 | 흐름의 단계 |
| --- | --- | --- |
| `app/` | 페이지, API 라우트 | 4, 5, 9 |
| `src/components/` | 입력창, 목록, 체크박스 같은 화면 부품 | 1, 2, 3, 10 |
| `src/lib/` | 저장 함수, DB 연결, Drizzle 설정 | 6, 7, 8 |
| `src/types/` | 화면과 서버가 같이 쓰는 할 일 타입 | 전체 |
| `docs/` | 명세 문서 | 없음 |

- Zod 규칙을 둘 위치(`src/types/` 또는 `src/lib/`)는 정해야 한다. 화면과 서버가 같은 규칙을 가져다 쓸 수 있는 곳이어야 한다.

## 6. 코드 규칙

- TypeScript strict 모드를 켠다. `any` 타입은 쓰지 않는다.
- 주석은 한국어로 짧게 쓴다.
- `console.log`는 디버깅이 끝나면 지운다.
- DB 접속 주소는 코드에 직접 쓰지 않고 환경 변수(`.env.local`)에 둔다. 이 파일은 git에 올리지 않는다. (v0.3부터)

## 7. 테스트 방식

- 화면 테스트: React Testing Library로 입력, 클릭, 체크를 사용자처럼 해 보고 결과를 확인한다.
- 검사 규칙 테스트: Zod 규칙에 1자, 100자, 빈 제목, 101자를 넣어 결과를 확인한다.
- 테스트 목록은 `TEST_CASES.md`에서 정한다.
- 테스트는 삭제하거나 건너뛰지 않는다. 실패하면 구현을 고친다.
- 실행 명령: `npm test`

## 8. 확인이 필요한 사항

- **PRD 7절 미결 사항:** v0.1 데이터 유지 방식, 공백만 있는 제목 처리, 삭제 확인 창. 이 세 가지가 정해져야 3절과 4절의 3단계가 확정된다.
- **오류 처리:** 4단계 요청이 실패하면(서버 꺼짐, DB 오류) 화면에 무엇을 보여줄지 정해야 한다.
- **Zod 규칙 위치:** 5절 참고.
